**Purpose:** One place that lists every auth layer tollgate has (or is building), why each one exists,
and — critically — what it actually looks like to the user. This is the user-facing/product summary;
`docs/AUTH-PLAN.md` has the full option brainstorm and trade-off analysis, and root `PLAN.md` carries
the detailed, file-by-file implementation plan for whichever layer is currently being built. Updated
as each new layer ships or gets planned.

## Layer 1: Email + password — **IMPLEMENTED** (2026-07-25)

**What it is:** The base credential check — Better Auth's `emailAndPassword` provider, scrypt-hashed
passwords, an httpOnly `SameSite=Lax` session cookie scoped to the user's organization (one org per
account, auto-created on first sign-in). Hardened by a progressive, self-resetting lockout keyed to
the account's email: 5 consecutive failed sign-ins locks that account out, starting at a 5-minute
cooldown and doubling on each repeat (5 → 10 → 20 min → … capped at 24h), auto-resetting after a day
of inactivity. A separate per-IP rate limit backstops it against spray attacks across many accounts.

**Why it's there:** This is the floor — "something you know" has to be proven before anything else is
even considered. The lockout exists because a password check by itself doesn't stop an attacker from
simply guessing or automating their way through it; without it, "email + password" would only be as
strong as the weakest password in use.

**What the user sees:**
- A sign-in/sign-up form; on success, landing directly on the dashboard with their email shown
  top-right and a **Sign out** control.
- On a wrong password: a generic "Invalid email or password" — no hint about whether the email exists
  at all. Once down to their last 3 attempts, the message gets specific: "2 attempts remaining before a
  temporary lockout," etc.
- After the 5th failure: the form disables itself and shows a live countdown ("Try again in 4:52") that
  persists even if they refresh the page. A correct password entered during that countdown is still
  rejected — the lock doesn't lift just because they finally typed it right.
- A successful sign-in at any point clears all of this — the next mistake starts the count fresh.

## Layer 2: TOTP two-factor authentication — **IMPLEMENTED, opt-in** (2026-07-25, revised 2026-07-26)

**What it is:** An optional second step after the password: a live 6-digit code generated by an
authenticator app (Google Authenticator, 1Password, Authy, etc.) already on the user's phone, via
Better Auth's `twoFactor` plugin. Not email- or SMS-delivered — the code is generated locally by the
app from a secret set up once at enrollment, and never travels over the network again after that.

**Why it's there:** Layer 1 alone has one hard failure mode — if a password is phished, reused from
another breach, or leaked, it's simply *correct*, and a correct password is currently game over (full
access to mint spendable agent tokens, move budget caps, undo emergency freezes). TOTP closes exactly
that gap: Better Auth's plugin withholds the session cookie entirely until the second factor is also
satisfied, so a correct-but-compromised password alone stops being sufficient for accounts that turn it
on. It was picked over an email-delivered code specifically because tollgate has no email-sending
infrastructure or email verification today — TOTP needs neither, costs nothing to run, and isn't
undermined by "the attacker also controls the inbox." **Enrollment is opt-in** (revised 2026-07-26 —
originally shipped 2026-07-25 as mandatory-for-everyone, see `PLAN.md` §6): every new account is asked,
encouraged, but never forced, and every account can toggle it from Settings at any time.

**What the user sees:**
- **Right after creating an account:** a screen encouraging them to turn it on ("makes it
  significantly harder for someone else to get into your dashboard, even if they get hold of your
  password"), with an **"Enable two-factor authentication"** button and a **"Skip for now"** button.
  Skipping goes straight to the dashboard — nothing is blocked either way.
- **One-time setup (~2 minutes), from that prompt (or later, self-serve from Settings):** hit "Enable
  2FA," scan a QR code with their phone's authenticator app (or type in a manual key), then enter one
  code back to confirm it worked.
- **Immediately after, a one-time screen of 10 backup codes** they're required to acknowledge saving
  before they can move on — these are the only way back in if they lose their phone.
- **On every sign-in from a browser/device that isn't already trusted** (only for accounts that turned
  it on): after the normal email+password step, a second screen asking for their 6-digit code. They
  open the authenticator app, type what it shows, and they're in.
- **"Trust this device" checkbox** on that screen — checking it means that browser won't ask again for
  30 days, so a daily user on their usual laptop sees the extra step once, not every login.
- **Lost their phone?** A "Use a backup code" link on the same screen, one-time-use.
- **In Settings:** a single toggle-like card — "Enable 2FA" if it's off, or "Disable 2FA" /
  "regenerate backup codes" if it's on — both directions requiring the password to be re-entered first.
  Disabling is a genuine opt-out (no re-enrollment forced afterward), consistent with it being opt-in.

**What it doesn't cover:** an already-open session — TOTP protects *getting in*, not what a session
that's already open (or a stolen/replayed cookie) can do once inside. That's Layer 3 (step-up
re-authentication on the specific actions that mint tokens, move budgets, or undo freezes), covered
separately in `docs/AUTH-PLAN.md` §4 — not yet built or scheduled.

9. On the challenge screen, try **"Use a backup code instead"** with one of the 10 codes → confirm it
   works once, and fails if you try that same code again.
10. Visit `/settings` on the enrolled account → confirm "Regenerate backup codes" and "Disable 2FA"
    both prompt for your password before doing anything, and that disabling flips the card back to an
    "Enable 2FA" state with full dashboard access retained afterward.

Until this pass happens, treat the UI layer as unverified even though the underlying api contract is
solid.
